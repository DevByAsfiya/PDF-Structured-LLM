# Architecture & Engineering Decision Log

This document is an append-only record of notable architectural and engineering decisions made throughout the JAL Catalogue Scraper project.

Each entry captures:
- **Date**: When the decision was made.
- **What Was Decided**: The chosen technical approach, architecture, or policy.
- **Why**: Rationale, technical advantages, and business/accuracy context.
- **What Was Rejected**: Alternative approaches evaluated and why they were declined.

> **Instruction**: Append a new entry at the end of every phase. Never modify or delete previous entries.

---

## 1. Deterministic Extraction over LLM Extraction

- **Date**: 2026-09-04
- **What Was Decided**: Extract all SKU codes, prices, descriptions, and image-to-caption bindings deterministically using PyMuPDF text spans, bounding-box geometry, and regular expression grammar across stages 00–06. Restrict LLM usage strictly to downstream semantic enrichment (attribute normalisation, search blurb writing, taxonomy proposal, and natural-language recommendations).
- **Why**: The source document (`JAL FAUCETS 2025.pdf`) contains a clean, high-fidelity embedded text layer generated by PDFium with Type0/TrueType fonts. Deterministic parsing is 100% reproducible, runs locally with zero API cost, executes in milliseconds, and eliminates hallucinations. Catalogue prices directly drive client quotation sheets and Bill of Materials (BOM) generation where incorrect numbers represent costly commercial errors.
- **What Was Rejected**: Multimodal Vision LLMs (e.g. GPT-4o / Gemini Vision) directly parsing page images; optical character recognition (OCR) engines in the primary path; prompting LLMs to structure raw unparsed text into product tables.

## 2. Statistical Category-Level Price Tiering over LLM Judgement

- **Date**: 2026-09-04
- **What Was Decided**: Compute product price tiers (Value, Mid, Premium, Luxury) strictly statistically using MRP quantiles grouped within each specific product category using SQL/pandas.
- **Why**: Faucet and plumbing fittings span drastically different price ranges depending on the fixture type (e.g. a ₹1,594 concealed stop cock versus a ₹17,664 thermostatic basin mixer). Computing global percentiles across the whole catalogue would distort category economics, and relying on LLM judgements yields subjective, non-reproducible tier assignments. Statistical quantiles per category provide objective, mathematically explainable market segmentations.
- **What Was Rejected**: Global catalogue-wide price quantiles; hardcoded arbitrary rupee thresholds across disparate categories; LLM prompt-based classification of products into "budget", "mid-range", or "luxury".

## 3. Product-owns-Variants Hierarchy for Image-to-SKU Relationships

- **Date**: 2026-09-04
- **What Was Decided**: Model catalogue entities using a `Product`-owns-`Variants` hierarchical schema. A `Product` represents the physical fixture shown in an image (holding visual assets, series name, page number, and spatial bounding box), which owns one or more `Variant` records (holding individual SKUs, specific dimensions/sizes like 15mm vs 20mm, finish variants, and distinct MRPs).
- **Why**: Spatial analysis of the catalogue (e.g. page 33 / PDF page 40) reveals that a single product image frequently anchors a caption block containing multiple distinct SKUs (such as stop cock `82456` 15mm @ ₹1,992 and `82470` 20mm @ ₹2,066; or diverter combinations `82754`/`82750`). The visual-to-SKU relationship is strictly one-to-many. Modeling this explicitly prevents image duplication and reflects the physical layout of the catalogue.
- **What Was Rejected**: A flat 1:1 Product-to-SKU table (which would force image duplication or drop secondary variant SKUs); separate disconnected SKU tables lacking unified visual anchors.

## 4. Filesystem Asset Storage with Metadata in Database over Database BLOBs

- **Date**: 2026-09-04
- **What Was Decided**: Export extracted product images to the filesystem under `data/assets/` as converted sRGB WebP images (full resolution plus 400px thumbnails), storing only file paths, perceptual hashes (pHash via `imagehash`), dimensions, and binding metadata in SQLite.
- **Why**: Embedding thousands of high-resolution images as binary BLOBs inside SQLite causes massive database bloat, degrades page cache performance, complicates database migrations, and adds latency when streaming images into the Streamlit UI or CLIP/SigLIP embedding pipelines. Storing files on disk preserves a lightweight SQLite database and allows perceptual hash deduplication of reused product photos.
- **What Was Rejected**: Storing raw image binary BLOBs inside SQLite; storing base64-encoded image strings within SQLite columns or Parquet files.

## 5. Purge of Fabricated Constants and Establishment of Hard Rules 8 & 9

- **Date**: 2026-09-04
- **What Was Decided**: Remove all unverified and speculative constants (such as estimated series lists or guessed section boundaries) from `catalogue_spec.py`. Institute two immutable project rules in `AGENTS.md`: Rule 9 ("Never write a constant you have not read from the source document; leave values to be parsed at runtime") and Rule 8 ("No network calls in stages 00–06; pure functions over the PDF").
- **Why**: Pre-filling constants with guessed values introduces silent bugs and conflicts with source facts. The PDF contains an authoritative machine-readable INDEX page (PDF page 6) and prominent page headers; these must be parsed dynamically during runtime ingestion (Phase 1) to derive ground-truth series mappings and actual page offsets empirically.
- **What Was Rejected**: Hardcoding guessed series lists, static section page bounds, or estimated offsets without runtime verification from the PDF; relying on external web lookups or network APIs during early pipeline stages.

## 6. Phase 1 Source Verification & Document Findings

- **Date**: 2026-09-05
- **What Was Decided**:
  1. **INDEX Extraction**: PDF pages 6 and 7 contain an extractable, high-fidelity text layer. Page 6 lists primary faucet collections (Tansa, Nalini Pro, Kolab, etc.) and special finish ranges; page 7 continues with Showers, Thermostats, Bath Accessories, Necessaries, Sinks, and Spindles.
  2. **Empirically Derived Page Offset**: Verified the printed-to-PDF page offset across multiple pages (printed 01 -> PDF 8; printed 05 -> PDF 12; printed 31 -> PDF 38; printed 35 -> PDF 42; printed 47 -> PDF 54; printed 51 -> PDF 58). The offset is consistently **+7** (`pdf_page = printed_page + 7`).
  3. **Series Header Placement & Typography**:
     - Large series divider/intro titles appear at font sizes 24–48 pt (≥ 20 pt), often uppercase with wide letter spacing (e.g. `T A N S A`, `N A L I N I P R O`).
     - Product grid page headers appear in the upper header region ($y < 120\text{ pt}$) at font sizes 12–16 pt bold (e.g. `KOLAB`, `NALINI PRO`, `DRAS PRO`).
  4. **Product Content Boundaries**:
     - Front matter occupies PDF pages 1–7 (Page 1: Price effective date; Pages 6–7: INDEX).
     - Specialized finishes and concealed body products begin on **PDF Page 13** (Printed Page 6).
     - Main chrome faucet collections begin on **PDF Page 40** (Printed Page 33, TANSA).
     - Parts tables and accessory lists occupy end matter.
- **Why**: Probing the actual document structure eliminates all speculative assumptions before writing parsing logic.
- **What Was Rejected**: Hardcoding section page bounds or series names; attempting OCR/VLM on the index when clean text spans already exist.

## 7. Section Layout Template, Archetype Refinement, and Vector-Text Flagging

- **Date**: 2026-09-05
- **What Was Decided**:
  1. **Section Layout Template**: Verified that across all 21 faucet series, sections follow a strict, repeating 4-to-6 page structure:
     - **Page 1 (Hero)**: Full-bleed photograph featuring the collection title (e.g. `T A N S A`, `N A L I N I P R O`, `K O N A R`). Zero products, zero SKUs.
     - **Page 2 (Editorial)**: Editorial features, technical bullets (e.g. `Single lever mixers`, `Quarter turn ceramic disc faucets`, `Foam flow aerators`), and finish callouts. Zero products, zero SKUs.
     - **Pages 3 & 4+ (Product Grid)**: 3-to-4 column product cards with photo, SKU, description, and MRP.
     This explains why ~80 pages across the 202-page catalogue are legitimately product-free spreads rather than parser misses.
  2. **Archetype Disaggregation**: Rather than lumping all non-product marketing pages into `lifestyle`, split them into explicit archetypes:
     - `hero`: Full-bleed collection title and lifestyle hero opener.
     - `editorial`: Marketing feature bullets, technology overviews, and finish introductions.
     - `lifestyle`: General non-series marketing spreads and front matter imagery.
     - `tech_spec`: Technical drawings, installation instructions (e.g. Page 199 plumbing and warranty guidelines).
     - `parts_table`: Ruled table layouts, including Spindles & Cartridges (Pages 197–198) and Kitchen Sinks (Pages 188–193).
  3. **Kitchen Sinks Routed to `parts_table`**: Kitchen Sinks (PDF pages 188–193) do not use column cards; they use ruled tabular rows (`Cat. No. | Size | S.S. Grade | Finish | Thickness | Depth | Bowl | MRP`). They are classified as `parts_table` for Phase 3 tabular extraction.
  4. **Page-143 Vector-Text Discovery & Review Queue Flagging**:
     - On PDF Page 143 (UNOMIX Cartridge), a genuine product exists (`Cat No. 7736 Concealed Mixer Divertor with UNOMIX Cartridge MRP 4288/-`), but its text layer is rendered as 246 vector outline paths, making it invisible to standard PyMuPDF `get_text()`.
     - Across the entire catalogue, drawing-path scans confirm that Page 143 is an isolated anomaly for unparseable product text.
     - Added `has_vector_text: bool` to the `Page` model. Pages with high drawing counts (>20) and zero text-layer MRPs are flagged as `has_vector_text=True` for human review in Phase 3. No OCR or VLM is added to the primary deterministic pipeline.
  5. **Resolution of Confidence Floor Bug**:
     - Eliminated hardcoded constant floors (previously $\ge 0.85$) that made the `< 0.70` review threshold vacuous.
     - Implemented dynamic confidence tiers based on feature agreement (e.g. presence of MRP tokens, image-to-text pairing, template position consistency). Truly ambiguous or vector-text pages now correctly score in the 0.40–0.60 range to trigger the review queue.
- **Why**: Accurately mirrors catalogue reality, prevents false negative drops, isolates anomalous pages for human review, and restores meaningful confidence scores.
- **What Was Rejected**: Adding an OCR or VLM pipeline for vector text; forcing kitchen sink tables into a grid parser; treating hero openers as ambiguous failures.

## Phase 2: Product Grid Extraction (Stages 03–05)

- **Date**: 2026-09-06
- **What Was Decided**:
  1. **Column Inference via Centre Clustering**: Fixed a critical bug where wide images (e.g. Arctic spout) caused overlapping/spurious columns. Raw x-extent bounds were replaced with greedy 1D clustering of image `x_centres`, iteratively merging the closest pair of clusters until `≤ GRID_COLUMNS_MAX` (4) is reached.
  2. **Strict Caption Containment**: Prevented captions from bleeding into adjacent columns by restricting the caption search zone strictly to the parent column's x-boundaries (with zero horizontal drift tolerance). This ensures SKUs are bound only to the images directly above them.
  3. **Image Deduplication via Xref**: Solved duplicate extractions (e.g., `83456S25` twice) caused by identical raster image components reused in the PDF text layer. Bound images are deduplicated by `xref` ID before processing.
  4. **SKU > MRP Confidence Flag**: When the caption grammar tokenizer yields more SKUs than MRPs, confidence is forcefully reduced to `< 0.5` (specifically `0.4`). Instead of blindly guessing which SKU owns the price, these ambiguous captions are correctly flagged for manual review.
  5. **Parenthetical Compatibility Filter**: Filtered out parentheticals containing `Compatible` (case-insensitive) or a 3+ digit reference number from SKU parsing to prevent them from splitting the caption, while preserving genuine suffixes like `(QT)` or `(Tall Model)` in descriptions.
  6. **Regression Guard (Page 40)**: Locked in extraction accuracy for Page 40 as a permanent regression test. All 18 SKU→MRP pairs extract perfectly with 15 unique products.
- **Why**: Ensures 100% precision on price assignments (the critical accuracy gate) while deterministically flagging anomalous bindings for human review without introducing non-reproducible LLM guesses.
- **What Was Rejected**: Relying on raw x-extents for column width; using spatial tolerance for column bounds; guessing MRP ownership in malformed text blocks; stripping all parentheticals blindly.

## Phase 3: Parts Table Extraction, Edge Cases, and Deduplication

- **Date**: 2026-09-07
- **What Was Decided**:
  1. **Dual-Strategy Table Parsing**: Implemented `TableParser` for `parts_table` pages using `pdfplumber`. Spares tables (Pages 197-198) extract cleanly via pdfplumber's default ruled-line strategy. Kitchen Sinks (Pages 188-192) lack internal horizontal lines, returning 0 tables by default; they are parsed via a fallback zip strategy (`vertical_strategy="text"`, `horizontal_strategy="lines"`).
  2. **Kitchen Sinks Zip Strategy**: In the fallback path, cells return wrapped columns of text. These are split on `\n` and positionally zipped into rows. The target line count is derived from the SKU column; if fewer than half the columns match this count, the row block is abandoned to prevent misalignment.
  3. **Null-MRP Schema Fix**: Modified `schemas.Variant.mrp` to `Optional[float]` and removed `0.0` defaults in `caption_grammar.py` to strictly enforce Rule 11. Unparseable prices are stored as `None` and their confidence is dropped to `0.4` to route them to the review queue. Fixed `cli.py` to format `mrp=None` as `-`.
  4. **Wider Price Pattern & Header Dropping**: Widened `TABLE_PRICE_PATTERN` to accept `/-` suffixes (e.g. `9194/-`). Aggressively dropped header rows by applying `SKU_PATTERN` on the extracted SKU column; non-matching strings are discarded rather than parsed as malformed products.
  5. **Series Carry-Forward Bug Fix**: Removed stateful cross-page carry-forward of the series name (`current_series`). When a page lacks a prominent series header, it falls back cleanly to the printed section name from `sections.json` (fixing "Tizu" bleeding across pages 168-198).
  6. **Page-Level SKU Deduplication**: Implemented deduplication by SKU within `cli.py` per page, keeping only the highest-confidence instance of a variant. This eliminated nearly 200 duplicate product entries (e.g. page 169 had SKU 36505 six times).
  7. **GridParser Fallback for Tables**: If a page is classified as `parts_table` but `TableParser` yields 0 products, the pipeline falls back to `GridParser`. This safely handles edge cases like Page 193 (Kitchen Accessories), which was mislabelled as a table but contains standard grid captions (yielding 6 products).
  8. **Positional Table Inference & Page 196 Gap**: For tables lacking explicit header text in the extraction (where default pdfplumber lumps everything into a single cell), the parser attempts positional inference on the `text/lines` fallback: if the first column matches `SKU_PATTERN` and the last matches `TABLE_PRICE_PATTERN`, it treats them as SKU/MRP and caps confidence at `0.6`. Note: Page 196 (PTFE Tape) still yields 0 products due to severe pdfplumber cell merging that positional inference cannot untangle. These few products remain a known gap and must be manually entered.
- **Why**: Handles multi-strategy tabular extraction safely, eliminates silent pipeline assumptions, strictly prevents phantom data (like `mrp=0.0`), and ensures unparseable edge cases reliably land in the review queue rather than polluting the dataset.
- **What Was Rejected**: Hardcoding a `0.0` default for `mrp`; writing file contents via python strings in CLI commands; using hardcoded column-map overrides for single broken pages (e.g. page 196) rather than generalized inference.
